# 执行打包与交付（Delivery Package）

> 两档打包形态、实施纪律、验证清单与反馈编译。在 Stage 4 使用。
> 目标：让执行可控、验收有标准、反馈可执行。

## 0. 两档形态

| 执行场景 | 档位 | 形态 |
|---|---|---|
| 当前会话 AI 续作（上下文在手） | 轻档 | 方案卡完整记录内嵌一节"执行边界清单"：不做什么、验收标准、必须停下审批的停点。**不单独成文**——单独成文是和方案卡重复 |
| 派工给其他 Agent / AI Coding 工具 / 人，或跨会话执行 | 重档 | 完整开发任务包（PKG-###），这是唯一的上下文传递载体 |

## 1. 最小连贯增量

第一阶段只做一条可用的端到端闭环，排除吸引人但非必要的功能。后续阶段通过 delta-only 机制迭代。

## 2. 重档任务包必须回答七个问题

1. 为什么做这个？（业务背景）
2. 要求的确切行为是什么？
3. 复用什么、自建什么？（含已验证/未验证能力清单）
4. 什么不许动？
5. 什么明确不做？
6. 怎么算完成、怎么验证？
7. 哪里必须停下来等审批？

模板：[../templates/dev-task-package.md](../templates/dev-task-package.md)。

## 3. 实施纪律

- 改之前先看仓库现状；遵守仓库既有约定。
- 不引入不必要的依赖；未获批准不破坏向后兼容。
- 处理错误与空状态；补充或更新测试与黄金用例。
- 小步可审阅的增量；每个有意义的改动后测试。
- 不悄悄扩大范围；偏离已批准方案立即记录。
- 记录环境、决策、证据与回滚方式。

## 4. 验证清单（确定性优先）

1. schema 与确定性断言
2. lint 与类型检查
3. 单元与集成测试
4. 构建
5. 关键用户流测试
6. 持久化/重启测试
7. 权限与安全检查
8. 回归用例

跑不了的检查标灰并说明原因。

## 5. 交付报告

交付 = 详细证据 + 紧凑审阅包。审阅包含：变更摘要、测试与结果、已知限制与未测项、与任务包的偏差、风险灯、下一步所需审批、迁移或回滚说明。原始日志只作支撑证据。

## 6. 反馈编译

用户的口语反馈（如"功能能跑，但提示词入口太深，希望点击图片直接展开，不要影响拖动"）自动编译为结构化变更单：

- 当前行为
- 观察到的问题
- 期望行为
- 约束
- 影响范围
- 验收标准
- 回归检查
- 风险等级与所需审批

变更单赋 `CHANGE-###`，接入 baseline-and-delta.md 的 delta-only 循环。不让用户把反馈重写成正式 prompt。
