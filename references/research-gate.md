# 调研门（Research Gate）

> 触发条件、调研方法论与输出要求。在 Stage 2 使用。
> 目标：在发明新方案之前，先找到可用的现有方案，决定复用、改造、组合还是自建。

## 0. 触发与跳过

**必开**（满足任一）：

- 方案涉及选用开源项目、可比产品、可复用组件、框架或行业标准
- 存在"自己造 vs 用现成的"的真实取舍
- 用户明确要求调研

**可跳过**（必须在方案卡完整记录中写明理由）：

- 纯自有材料梳理、文档写作、非开发类任务
- 用户已指定具体实现
- 对现有系统的小改动
- 调研成本明显高于任务价值

## 1. 把任务拆成搜索轨道

从任务卡提取：问题域与目标用户、核心工作流与必备能力、技术与部署约束、隐私合规规模商用要求、期望产出。

拆成多条搜索轨道，而不是一个长查询。示例（图片+提示词管理系统）：

1. 完整的提示词管理应用
2. 数字资产管理系统
3. 无限画布与节点编辑器组件
4. 本地优先数据库与文件索引
5. 可视化知识管理工具

## 2. 信源分级

证据优先级从高到低：

1. 官方仓库与官方文档
2. release、源码、issue、PR
3. 维护者的技术文章或演示
4. 可信的第三方独立分析
5. 社区讨论（仅作补充证据）

不得把 AI 生成的摘要作为决策的唯一依据。

## 3. 候选漏斗

1. **广泛发现**：收集足够多的候选以理解解法空间。原始清单不展示给用户。
2. **硬过滤**：存在关键错配直接否决——问题域或架构不对、许可证不兼容、无源码或文档、无可行扩展路径、隐私或部署模型不可接受。
3. **决赛深比**：只深入比较 3–5 个认真候选。被过滤的候选记录原因即可，不逐个写长文。

## 4. 深度对比维度

| 维度 | 问题 |
|---|---|
| 功能契合 | 哪些需求现成？哪些缺失？ |
| 技术契合 | 技术栈是否匹配现有系统与团队？ |
| 架构 | 加所需功能会不会和它的设计打架？ |
| 维护 | 近期 commit/release？关键未决 issue？ |
| 文档 | 新开发者能否装起来并扩展？ |
| 许可证 | 修改、再分发、SaaS、署名、copyleft 义务？ |
| 集成 | API、数据模型、认证、构建系统、插件体系？ |
| 部署 | 本地/云/容器、依赖、资源负担？ |
| 安全隐私 | 遥测、外部服务、已知漏洞、数据暴露？ |
| 改造成本 | 适配、重写、隐藏耦合？ |
| 退出成本 | 数据和定制代码以后能否迁走？ |

## 5. 证据账本

每条承重结论记录：结论、来源与日期、证据类型（文档/源码检查/issue 或 release/运行时测试）、置信度、属于事实/推断/假设。

**缺证据标灰**——灰不是否定事实，也不是已验证能力。承重灰项是验证门（references/validation-gate.md）的触发条件。

## 6. 复用六分类

每个候选必须归入且仅归入一个主策略：

- **直接使用**
- **Fork 改造**
- **抽取组件**
- **组合使用**
- **仅作架构参考**
- **否决**

## 7. 打分与一票否决

1–5 分仅作决策辅助，总分不得掩盖致命伤。建议权重：功能契合 25%、改造成本 20%、技术契合 15%、维护 15%、许可证 10%、文档 5%、安全隐私 5%、退出成本 5%。

许可证、安全、隐私或架构的致命失败直接否决，覆盖总分。

## 8. 输出

用 [../templates/research-report.md](../templates/research-report.md)，结论必须包含：

- 首选候选或组合
- 明确复用哪些、改造哪些、自建哪些
- 备选被否决的原因
- 仍需验证的假设
- 最小验证实验建议
- 风险等级与需要人拍板的决策

报告全文进方案卡第三层；方案卡第一屏只呈现结论、推荐理由与待确认项（遵守审阅预算与叙事约束）。

## 9. 诚信规则

- 重要结论引来源；维护活跃度检查注明日期。
- 区分"仓库宣称"与"实际检查/运行验证过的行为"。
- roadmap 或 issue 里提到 X ≠ 支持 X。
- 无网络访问时，把输出标注为搜索计划或桌面评审。
